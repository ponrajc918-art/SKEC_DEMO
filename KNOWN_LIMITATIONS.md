# Known limitations and release gates

- The supplied Phase 0 register identifies unresolved programme, admissions, leadership, contact-email and image approvals. The site deliberately uses neutral copy and placeholders rather than inventing facts.
- SMTP delivery, Razorpay order creation/webhook verification, and local private file storage now have server-side adapters. They remain **unverified against real provider credentials**: no SMTP message, Razorpay transaction/webhook, or production deployment was executed for this delivery.
- Password reset, password change, invitation acceptance, session revocation, TOTP MFA enrolment/confirmation, rate limiting and audit events are implemented. An approved MFA authenticator workflow and production `FIELD_ENCRYPTION_KEY` must be set up before institutional use. The local Windows environment cannot load its installed cryptography native extension, so encryption-backed MFA enrolment was not run locally; the pinned Docker dependency is provided for the deployment environment.
- Private uploads are stored outside the web root, accept only PDF/DOCX/plain text, require a configured ClamAV daemon to mark them clean before download, and enforce owner/privileged-role access. Scanner-unavailable uploads remain inaccessible. The adapter has not been verified against a deployed scanner or real uploaded files.
- The production Compose topology now includes Caddy-managed HTTPS, private PostgreSQL/API networking and migration-before-start. Public launch still requires a real domain/DNS record, server access, generated secrets, approved content, backup/restore validation, independent security review and an institutional operating owner.
- Automated tests validate selected API workflows. They are not a penetration test, accessibility assessment, load test, disaster-recovery exercise, or production-readiness guarantee.
